# 이용제한 재발 조사 — 2026-11-02

## 현재 판단

**공개 차단 사례만으로는 AX 전송과 라이브 DB 조회의 원인 확률 순위를 정할 수 없다.**
초기 AX 우선 조사 판단은 앱과 서버에 동작이 전달되는 경로를 비교한 기술적 추정이며,
후속 사례 조사에서도 이를 뒷받침하는 DB/AX 분리 사례는 찾지 못했다.
카카오톡의 실제 탐지 원인은 미확인이며 확률을 산출할 대조 실험이나 서버 측 자료도 없다.
[공개 피해 사례 조사](2026-11-02-public-restriction-cases.md)를 함께 참고한다.

첫 제한과 이번 제한은 별개로 취급한다. 사용자는 첫 제한을 LOCO 태블릿 인증·테스트 뒤에
봤고, 같은 문구의 두 번째 제한은 LOCO 삭제 후 DB+AX 실험 뒤에 다시 발생했다고 확인했다.
LOCO 삭제만으로 과거의 서버 측 기록이 지워진다고 볼 수는 없지만, 그 이력이 이번 재발의
원인이라는 증거도 없다. 첫 제한의 원인 추정으로 두 번째 제한을 설명하지 않는다.

## 후보별 근거와 한계

| 후보 | 확인한 사실 | 아직 확인하지 못한 부분 |
|---|---|---|
| AX 전송 | 기존 앱에 `AXValue`와 `AXPress`를 호출한다. 접근성 요청은 앱의 접근성 메서드에서 처리할 수 있고, 전송은 앱의 실제 네트워크 동작을 일으킨다. | 카카오톡이 AX 동작을 별도로 기록하거나 제재에 사용한다는 증거는 없다. |
| 라이브 DB 조회 | 실제 조회 함수는 SQLCipher `-readonly -safe -noinit`을 사용하며, 해당 텍스트 조회 경로에는 네트워크나 AX 호출이 없다. | 읽기 전용이어도 WAL 공유메모리·잠금에 참여할 수 있다. 카카오톡이 이를 감시하는지는 알 수 없다. |
| 이전 비공식 접속의 잔여 영향 | 첫 제한이 LOCO 실험 뒤에 있었다는 사용자 확인. 다른 프로젝트에도 비공식 로그인 시도 뒤 제한됐다는 사용자 보고가 있다. | 이번 제한이 같은 원인인지 알 수 없다. 해당 외부 사례는 AX·DB 비교 실험이 아니다. |

AX 오류 `-25200` 자체는 계정 제재 증거가 아니다. 11월 1일 네 건은 AX 오류에도 새 메시지가
DB에 나타났으며, 오류를 이유로 다시 누르지 않았다. 또한 본인 채팅 네 건만으로 과도한
전송량이 원인이었다고 결론내릴 수 없다.

## 계정에 접촉하지 않은 격리 실험

2026-11-02, 실제 조회 함수로 합성 SQLCipher WAL DB와 그 복사본을 조회했다.
OS 샌드박스로 네트워크와 실제 카카오톡 컨테이너 파일 읽기·쓰기를 금지했다.
로컬 소켓 bind가 권한 오류로 거부되는 것도 확인했다. 실제 계정 DB, AX, 로그인은 사용하지 않았다.

| 항목 | 결과 |
|---|---|
| 네트워크를 OS에서 금지한 상태의 암호화 DB 조회 | 성공 |
| Python SQL 검사기를 우회한 뒤 SQLCipher 읽기 전용 연결로 쓰기 시도 | SQLCipher가 거부 |
| 조회 전후 본 DB·WAL의 SHA-256 | 각각 동일 |
| 조회 전후 원본 합성 DB의 `-shm` SHA-256 | 변경됨 |
| 쓰기가 멈춘 합성 DB와 WAL을 복사한 뒤 복사본 조회 | 성공 |
| 복사본에 별도 `-shm` 생성 | 확인 |

이 결과는 **읽기 전용이 곧 파일·공유 상태에 아무 흔적도 남기지 않는다는 뜻은 아니라는 점**을
확인한다. 실제 카카오 DB의 공유메모리를 측정하거나, 카카오가 이를 탐지하는지 시험한 것은 아니다.
반면 복사본 분석은 카카오 앱·네트워크와 분리할 수 있음을 확인했다.
상세 값은 같은 폴더의 `2026-11-02-offline-db-audit.json`에 있다.

실험의 복사는 쓰기가 멈춘 합성 DB에서 했다. 실행 중인 실제 DB의 본 파일과 WAL을 순서대로
복사하면 서로 다른 시점이 섞일 수 있으므로, 이 실험을 실시간 스냅샷 구현 검증으로 취급하지 않는다.
복사본 취득 과정과 취득 후 분석은 별도 단계다.

## 자동화 범위를 확인하는 절차

현재 제한 계정에서 추가 전송으로 한계를 탐색하지 않는다. 기능 실험과 계정 제재 관찰을 분리한다.
제한이 해제된 뒤 정상 수동 이용이 안정적인지 먼저 확인하고, 같은 앱 버전·기기·접속 환경에서
아래 한 단계씩만 추가한다. 계정 이력의 잔여 영향 때문에 같은 계정의 순차 실험에는 인과 추론의 한계가 있다.

1. **복사본만 분석:** 검색·요약·답장 작성은 원본 앱이나 서버 접촉 없이 확인한다.
2. **라이브 DB 조회만:** AX·미디어 다운로드·자동 로그인·전송을 모두 끄고 조회만 분리한다.
3. **AX 컨트롤 조회만:** DB 연결 없이 이미 열린 본인 창의 입력창·버튼 속성만 확인한다.
4. **AX 입력만:** 빈 본인 입력창에 합성 초안을 넣고 전송하지 않는다. 초안 처리가 네트워크와
   무관하다고 가정하지는 않는다. 실제 전송이 필요하면 사용자가 직접 처리한다.
5. **AX 전송만:** DB 사전 조회·전송 확인 없이 이미 확정한 본인 창에서 명시적인 테스트 1건을
   전송한다. 수신 확인은 사용자가 휴대폰에서 한다. 결과 불명확 시 재전송하지 않는다.

각 단계에서 시작·마지막 동작·마지막 정상 확인·첫 제한 확인 시각, 코드 버전, 사용 기능을
기록한다. 전송 직후 성공뿐 아니라 이후 정상 사용도 관찰해야 한다. 지금 자료로는 적정 관찰 기간을
산출할 수 없으며, 잠시 제한이 없었다는 결과를 무제한 사용 보장으로 바꾸지 않는다.

DB만 사용한 구간에서 재발하면 AX 없이도 발생한 것이고, AX만 사용한 구간에서 재발하면 그 구간의
DB 연결은 필수 조건이 아니었던 것이다. 어느 경우든 과거 활동의 지연 효과까지 한 번에 배제되지는 않는다.
두 단계를 다시 합치기 전에 각 결과를 따로 평가한다. 반복 제재를 목표로 한 빈도·한도 탐색은 하지 않는다.

현재 확인 가능한 가장 분명한 경계는 **취득이 끝난 복사본의 로컬 검색·요약·답장 작성**이다.
라이브 DB 접근과 AX 전송은 기능상 가능하지만, 제재 없이 지속 사용 가능한 범위는 아직 확정하지 못했다.
키보드 입력·클립보드 등으로 전송 방식만 바꾼다고 제재 원인이 제거된다고 가정하지 않는다.

## 조사 범위와 출처

- 이 조사에서 추가 메시지 전송·로그인·실제 대화 DB 조회는 하지 않았다.
- 저장된 전송 저널·소스·이 채팅 기록·앱 로그 파일 형식·실행 프로세스를 읽었다.
- 확인 시점에 LOCO/태블릿/해당 전송 헬퍼와 일치하는 실행 프로세스와 관련 LaunchAgent는 찾지 못했다.
  프로세스 명령행 패턴과 두 LaunchAgents 디렉터리를 대상으로 한 확인이며 과거 실행 여부를 증명하지 않는다.
- 앱의 본 로그는 인코딩된 형태여서 이번 조사로 제재 적용 시각·원인 코드를 읽지 못했다.
- [Apple 접근성 구현 문서](https://developer.apple.com/library/archive/documentation/Accessibility/Conceptual/AccessibilityMacOSX/ImplementingAccessibilityforCustomControls.html): 값 setter와 action 메서드를 앱이 구현하는 구조. 카카오톡의 탐지 구현 증거는 아니다.
- [SQLite WAL 형식](https://sqlite.org/walformat.html), [읽기 전용 WAL](https://sqlite.org/wal.html#read_only_databases): 공유메모리와 잠금, 읽기 전용 연결 조건.
- [비공식 로그인 뒤 제한됐다는 원 사용자 보고와 유지관리자 답변](https://github.com/JungHoonGhae/openkakao-cli/issues/22): 프로토콜·버전·인증 경로가 이번 구현과 같다는 뜻은 아니며 비교 사례로만 사용했다.
- [카카오 자동감지 안내](https://talksafety.kakao.com/measure): 이용환경·이용패턴을 사용한다는 설명. DB/AX 탐지 기준은 제시하지 않는다.

계정 식별자, 방 ID, 실제 대화 본문, 인증 정보는 이 문서와 결과 JSON에 포함하지 않는다.
